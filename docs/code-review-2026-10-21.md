## 已确认的缺陷

### R1 令牌切换后的旧响应会污染当前缓存

位置：[dsh-github/lib/http.js](../dsh-github/lib/http.js)，170–180、325–335 行。

请求开始时，客户端比较 token 与 `lastToken`，变化就清空缓存。但缓存键只有 method、URL 和 Accept；异步响应完成时，没有再次验证该响应是否仍属于当前凭证。

复现顺序：使用合成令牌 A 请求私有资源并挂起；移除令牌，匿名请求另一资源以触发清空；让 A 的旧请求完成；再次匿名请求原私有资源。结果是 `fromCache: true`，返回 A 得到的私有数据，整个过程只有两次模拟网络调用。

影响限定在同一插件实例的进程内缓存：移除令牌或换成权限更低的令牌后，后续工具调用仍可能读到之前的授权数据。这不是已经发生真实泄漏的证据，但证明当前清缓存逻辑无法建立可靠的凭证边界。

建议为请求捕获凭证代次，响应提交缓存前确认代次仍有效；必要时按凭证身份隔离缓存。代次方案应覆盖 A → B → A 的交错，避免只比较 token 字符串。不要把明文 token 写入日志或可序列化缓存键。

验收：覆盖旧请求晚于切换完成、A → 匿名、A → B → A、304 重验证和请求取消；旧代次响应不得进入当前缓存，匿名请求应重新访问模拟服务并得到拒绝或公开结果。

### R2 固定估算日期进入已发布年份并改变峰谷判定

位置：[shared/tariff/index.js](../shared/tariff/index.js)，59–64、293–305、318–331、383 行。

固定列表把每年 2 月 1 日起七天作为春节近似值。`holidayProvenance()` 和 `holidayDatesForYears()` 对所有请求年份补入这些日期，只检查单个日期是否已存在，没有区分“该年日历已发布”和“该年尚无数据”。来源中的 `holiday: false` 又在解析阶段被丢弃，无法阻止估算日期重新加入。

离线 fixture 明确把 `2026-02-02` 标为非假日，并包含另一个假日。仅用来源日期时，`2026-02-02T02:00:00Z` 判为 peak；合并固定日期后变成 offPeak。此用例验证数据优先级，不依赖对真实年度放假安排的断言。

影响同时覆盖 Host 费用、费用客户端的峰谷展示和侧边栏倒计时。现在的来源分桶能说明日期来自 fixed，却不能防止估算改变金额；单纯在 UI 显示“估算”不能解决已取得数据被覆盖的问题。

建议引入逐年的 `published / unavailable / invalid` 状态及明确的非假日集合。完整有效日历应优先于固定估算；对只有部分日期的来源，应明确其覆盖范围。无法可靠定位的春节日期只用于带估算标识的展示，是否参与金额计算应有单独策略。修改 canonical 模块后再生成三份副本。

验收：来源明确排除的日期不得被 fixed 加回；已发布年份和未发布年份分别测试；Host、两个客户端在相同政策下保持一致；manual 覆盖规则有明确测试。

### R3 重试时间被记录却没有用于计费

位置：[dsh-token-cost/index.js](../dsh-token-cost/index.js)，1309–1325、1393–1401 行。

`llm/retry-started` 更新 `attemptStartedAt`，并清除同一 step 的替换标记以保留前一次计费。但 `contributionOf()` 只读取 `stepStartedAt`，因此重试仍继承首次请求的峰谷和费率段。

进一步核对本机 DSH 0.2.1-rc.2：`dsh-llm-retry` 在退避等待结束后、返回 retry 决策前写入 `llm/retry-started`；`dsh-agent-loop` 在同一个 `step()` 的内部循环重试，不重新发出 `step/start`。因此首次 step 时间不会被宿主自动刷新，这一问题确实对应宿主的重试事件顺序。

复现使用合成费率：输入 4 单位每百万 token，谷时倍率 0.5。首次请求在周一 03:59 UTC，重试在 04:01 UTC，各使用 100 万输入 token。正确结果应为一次 peak、一次 offPeak，共 6 单位；当前结果为两次 peak，共 8 单位。反向跨界也会少计，跨费率段同样会选择错误费率。

建议优先读取有效 `attemptStartedAt`，再回退 `stepStartedAt` 和事件时间；保留新 step 清零、同一次 attempt 更新样本只替换一次的规则。

验收：补上 peak → offPeak、offPeak → peak、跨费率版本、多次重试，以及 attempt 后 final 替换用例。现有重试测试使用相同 `NOW`，只证明调用数相加，无法验证时间边界。

### R4 等待审批期间关闭写入仍会发出 POST

位置：[dsh-github/lib/tools.js](../dsh-github/lib/tools.js)，124–155、718–728 行；另两个写工具复用同一守卫。

`ensureWriteAllowed()` 在等待 `approval.request()` 前读取 `allowWrites`，审批返回后只检查结果是否为 `allowed-once`，没有重新检查实时配置。此配置本身是可即时更新的。

复现：打开写入并挂起审批，把 `allowWrites` 改为 false，再返回 `allowed-once`。模拟客户端仍收到一次 POST，此时配置读取结果确实为 false。

建议把写入前的最终政策校验集中到统一路径。审批完成后重新验证写开关与取消状态；若凭证解析等后续步骤仍有异步等待，在即将发送请求时也校验政策代次。撤销写权限应让尚未发送的操作失效，避免恢复开关后复活旧操作。

验收：三个写工具都覆盖审批期间关闭写入、取消、凭证异步等待期间撤销，以及正常允许操作；已撤销的请求数必须为零。保留现有拒绝、审批服务缺失和异常时拒绝写入的行为。

### R5 时钟刷新一部分年份失败时会覆盖有效缓存

位置：[dsh-sidebar-clock/client.js](../dsh-sidebar-clock/client.js)，734–749 行。

`Promise.allSettled()` 后只收集成功年份，只要有一个成功就重建整个两年日历、标为 `live` 并写入 localStorage。失败年份原来成功获取的日期没有合并回来，实际行为与函数注释中的保留旧日历不一致。

复现：先成功取得包含 `2026-04-06` 的两年合成日历；第二轮让 2026 年失败、2027 年成功。结果中该日期消失，写入缓存的副本也失去它，状态仍为 `live`。

建议按年份保存最近成功数据及抓取时间，仅替换本次成功且有效的年份；部分失败应保留错误和旧数据状态，并对失败年份单独重试。Host 已有部分失败保留年份数据的实现，可共享语义，但先修好 R6 的有效性判断。

验收：当前年失败、次年失败、两年都失败、跨年、旧缓存恢复五种场景；失败年份原有非固定日期必须保留，不能因另一年成功而刷新其成功时间。

### R6 业务错误响应会被记录为成功且删除日历

位置：[dsh-token-cost/index.js](../dsh-token-cost/index.js)，2145–2189 行；[shared/tariff/index.js](../shared/tariff/index.js)，357–407 行；时钟的 `fetchHolidayYear()` 也使用同一宽松解析结果。

Host 在 HTTP 成功和 JSON 解析成功后立即设置 `responded = true`。`parseHolidayPayload()` 对未知结构返回空数组，因而 `{ "code": -1, "message": "synthetic upstream failure" }` 被当作有效空日历。

复现先成功载入合成日历，再让两年都返回该错误对象。原来的非固定日期被删除，`error` 仍为 null，`fetchedAt` 更新到失败轮次的时间，短退避也不会触发。

建议解析层返回结构化结果，区分有效数据、合法空日历、未发布年份、业务错误和未知格式。只有被确认有效的数据可以替换旧缓存；部分年份失败也应在状态中可见。不能用“日期条数必须大于零”代替结构验证，否则会拒绝合法空结果。

验收：HTTP 200 错误对象、null、未知对象、业务失败码、合法空日历、合法数据、仅一年失败；失败必须保留最近成功值及其时间，并进入正确的重试路径。

### R7 仓库解析丢弃主机导致操作目标可能偏移

位置：[dsh-github/lib/repo.js](../dsh-github/lib/repo.js)，36–43、63–82 行。

SCP 格式接受任意 hostname，URL 分支只取 pathname。于是 `https://gitlab.com/example/project` 和 `git@gitlab.com:example/project.git` 都变成 `example/project`，随后默认发往 `https://api.github.com`。

常见结果是报错或读到 GitHub 上的同名仓库。如果该同名仓库存在且当前凭证有写权限，经过现有写入策略后还可能向错误平台目标写入。审批理由仅显示 owner/name，无法提示原始 hostname 已被丢失。

建议保留解析结果的 host，并与配置的 GitHub 服务匹配；显式 owner/name 继续作为当前服务的简写。自动检测遇到 GitLab 或其他主机时应要求显式提供目标。GitHub Enterprise 的网页、SSH 主机与 API base 路径应有明确映射，不能通过接受任意 host 来隐式支持。

验收：GitHub HTTPS、SCP、网页深链接、配置的 Enterprise、GitLab URL、GitLab origin、同名跨平台仓库；非目标主机不得静默降成 owner/name。

## 历史重建限制

### R8 完整重建依赖已经丢失的进程内费率目录

位置：[dsh-token-cost/index.js](../dsh-token-cost/index.js)，847–893、2249–2255、2303–2310 行。

费用目录从 fallback 开始存于内存，抓取后的费率以本次抓取时间生效。投影检查点确实保存了使用过的 epochs，所以**保留有效检查点的恢复能维持金额**。但如果必须从日志完整重建，初始化使用的是新进程目录，原抓取时间线不在原始使用量事件中。

复现以合成费率把输入单价从 4 改为 8：旧目录下的历史请求金额为 8；新目录直到重启后的新抓取时间才生效，同一日志完整重建变为 4；直接恢复旧状态再同步新目录仍为 8。

这个触发条件与当前宿主契约吻合：安装包的 `dsh-session-projection` 会丢弃版本不匹配的 checkpoint，并从 `init` 重放；未挂载持久投影缓存的组合在重启后也依靠日志重建。不能将此结论扩大为“每次重启都会改历史金额”。

建议把定价依据提升为可恢复的持久事实，例如保存独立的带生效时间费率目录，或通过支持的宿主接口记录计价依据事件。历史目录确实缺失时，应标记“无法恢复原计价依据”，明确区分重新估算值和原已记录金额。不要在同步 fold 中加入网络或异步 I/O。

验收：保存检查点后恢复、无检查点全量重放、stateVersion 升级、离线重启、跨费率段回放，分别验证金额及来源状态。修 R2 或 R3 时尤其要考虑旧金额是保持记录还是重新计算，不能仅递增 stateVersion 后默认重新定价。

## 后续优化建议

以下是结构和体验改进，并非已经测得的线上性能故障。建议在上述正确性修复之后分批实施。

| 优先级 | 建议 | 代码依据与验收方向 |
|---|---|---|
| P2 | 分离 Host 计价领域模块 | `dsh-token-cost/index.js` 同时包含页面解析、目录、事件折叠、视图和刷新调度。沿现有纯函数边界逐步拆分 pricing、projection、refresh 模块，先保持 exports 和状态行为，使用现有回放验证等价；无需引入新框架 |
| P2 | 扩充解析器的价格不变量 | `parsePricingPage()` 381 行仅以 cache-hit 的谷峰比推导所有 token 桶倍率。若未来各桶折扣不同，会继续解析成功却错误计价。先加“不同比例时拒绝解析并降级”测试，再决定是否支持逐桶倍率；本次没有证据说明当前在线页面存在该差异 |
| P2 | 限制响应和缓存的总字节数 | GitHub HTTP 层先完整 `response.text()`，缓存同时保留文本和 JSON；128 条是数量上限，`maxOutputChars` 只是后续输出截断。增加响应体预算和缓存总字节预算；超预算应给出明确错误，不得把截断 JSON 当成功 |
| P2 | 验证异步数据能主动更新页面 | `onStatus` 是空函数；子会话更新只写 `ownAmounts`，未见主动发布父会话视图的逻辑。需用真实宿主验证“父会话无新事件，仅子会话费用变化”和“仅刷新失败状态变化”的页面更新；是否被宿主其他快照读取补足，本次未作端到端确认 |
| P2 | 补真实 React 交互覆盖 | 客户端测试主要使用 React/DOM stub。增加设置保存成功与拒绝、revision 冲突、token 清除、弹层键盘操作和焦点返回测试。`CostPill` 有 Escape 关闭，但未见打开时移入焦点和关闭后返回按钮的处理；应先确定弹层是非模态还是模态再设计焦点行为 |
| P2 | 明确测试通过与跳过 | 统一 runner 把退出码 0 计为 PASS，安装包缺失的 SKIP 也包含其中。单独统计 passed/skipped，并设一条要求真实 DSH 安装包的发布验证路径；普通 CI 可继续运行离线 fixture |
| P2 | 给打包流程补自动校验 | 当前 CI 只运行 `npm test`。发布验证应在隔离目录打包两次比较 hash、解包检查 exports/patch/files 和许可证材料完整性，再运行装包契约检查；将共享副本一致性检查纳入打包前置步骤，避免独立执行 pack 时分发漂移副本 |
| P2 | 更新面向当前版本的文档入口 | 根 README 仍有 GitHub “Host-only / no UI surface”的表述，与已实现的设置页矛盾；旧 reflections 也列出已完成的待办。保留其历史日期，新增当前状态入口并链接本报告，避免把历史建议当作现状 |
| P3 | 测量后再减少重复计算 | 每个事件都构造 `catalog.epochsFor(Date.now())`；每个币种的 view 都重新聚合模型与子树。先对多费率段、大会话、多子会话测耗时和分配量，再按目录版本及日历年份缓存不可变快照，避免破坏历史状态或显示币种正确性 |
| P3 | 降低时钟的周期性开销 | `ClockWidget` 每秒重渲染，`dateLine()` 每次构造两个 Intl formatter。可缓存 formatter、把日期和倒计时拆成较慢节拍、页面不可见时暂停刷新并在恢复时立即校时；以实际 profile 决定收益，保留现有分钟级峰谷切换缓存 |

对 `ownAmounts` 和仓库检测缓存，也可以补容量及生命周期设计；清理子会话缓存时必须把缺失数据标成 unknown，不能让总费用静默减少。请求合并等 HTTP 优化应在 R1 修好之后再做，并保持不同调用方的取消相互独立。

## 建议实施顺序

1. **凭证与写入边界**：修 R1、R4，并把撤销和并发用例加入 GitHub 测试。随后处理 R7 的目标主机校验。
2. **日历数据契约**：一起处理 R2、R5、R6，建立逐年有效性、来源优先级、失败保留和重试语义，再生成共享副本。
3. **计价时间与恢复**：修 R3，明确 R8 的持久化与迁移方案；同时验证旧检查点和全量重放，避免一次修复改坏历史费用。
4. **工程与体验**：拆分模块、补真实客户端交互和发布验证，再依据测量处理热点。

每批保留一个小的可审查变更，先添加描述期望行为的失败测试，再修实现并运行相关测试与完整 `npm test`。本次证据脚本固定的是缺陷表现，不能直接作为“修复后应保持通过”的回归测试。
